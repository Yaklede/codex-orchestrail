# 토큰 효율 예비 검증 — 2026-09-15

**이번 작은 버그 수정 작업에서는 Orchestrail의 Builder 위임 경로가 토큰을 절감하지 못했다.** 같은 기준으로 평가했을 때 Sol 단독과 같은 경계값을 놓쳤고, 메인 에이전트의 관리 작업이 전체 사용량의 88.3%를 차지했다.

이 결과는 작업 하나를 방식별로 한 번 실행한 관측이다. 자동 라우팅의 평균 효율, 장기 세션의 효율, 복잡한 판단에서 Astra를 호출하는 효과를 검증한 것은 아니다.

## 실행 조건

- Codex CLI 0.154.0, Node 22.14.0, macOS, 기존 Codex 로그인 사용.
- 의존성 배치 계획 함수의 검증·정렬·순환 감지·입력 불변성 수정.
- 같은 시작 커밋 `68800214591a1e9716f82ad0eb3c9efc1f9b5977`, 같은 명세와 공개 테스트, 별도 임시 체크아웃.
- 순서: Sol/high → Astra/high → Orchestrail(Sol/medium 메인 + Sol/high Builder).
- Orchestrail에는 Builder 한 번의 위임을 명시적으로 요청했다. 메인은 독립적으로 명세를 검토하고 검증을 준비했다. Expert 호출은 강제하지 않았고 실제로도 없었다.
- 실행당 360초 제한. 세 실행 모두 시간 안에 정상 종료했다. 모델에 수정 재시도를 요청하지 않았다.

이것은 **지정한 위임 경로와 단독 실행의 비교**다. 작은 작업을 메인이 직접 처리하도록 두는 Orchestrail의 선택 경로는 별도 검증이 필요하다. 모델·추론 설정도 실험 조건의 일부이므로 순수한 라우팅 효과만 분리한 실험은 아니다.

| Sol/high 단독 | 136,128 | 15,877 | 115,072 | 5,179 | 2,604 | 196.1초 | 38/39 |

¹ 추론 출력은 출력 토큰에 포함된다. 총토큰은 일반 입력 + 캐시 입력 + 출력이며 추론 출력을 다시 더하지 않는다. 이번 실행들의 cache-write input은 모두 0이었다. 이 수치는 청구액이나 주간 한도 차감량이 아니다.

하네스의 관측 총토큰은 Sol 단독의 **8.60배**, Astra 단독의 **12.70배**였다. 일반 입력도 각각 약 7.31배, 5.58배였다. 품질 기준을 모두 충족한 하네스 결과가 없으므로, 성공한 동일 품질 결과를 기준으로 한 절감률은 산출하지 않는다.

### 테스트와 소스 검토

처음 정한 38개 평가 테스트는 세 결과 모두 통과했다. 소스 검토에서 기존 명세의 다음 조건에 해당하는 경계값이 빠져 있음을 발견했다.

> when present it must be an array

`dependsOn` 속성을 생략하면 `[]`로 처리하지만, 속성을 명시하고 `undefined`를 넣으면 배열이 아니므로 `TypeError`여야 한다. Sol 단독과 Orchestrail 결과는 명시적인 `undefined`도 생략한 값처럼 처리했다. Astra는 거부했다.

이 조건을 39번째 테스트로 추가해 **이미 생성된 세 결과에 똑같이 다시 적용**했다. 모델은 수정하거나 재실행하지 않았다. 원래 38개 테스트의 결과와 이후 평가를 구분해 [집계 JSON](../benchmarks/results/2026-09-15-pilot.json)에 기록했다. 테스트 통과 여부와 명세 충족 여부를 구분해야 한다는 점도 이번 검증에서 확인했다.

## 사용량이 커진 구간

| Orchestrail 구성 | 총토큰 | 비중 |
| --- | ---: | ---: |
| 메인: Sol/medium | 1,034,524 | 88.3% |
| Builder: Sol/high | 136,622 | 11.7% |

Builder의 사용량은 Sol 단독의 136,128토큰과 비슷했다. 이 작업에서는 위임받은 구현의 사용량이 줄지 않았고 메인 작업이 추가됐다.

관측한 원인과 후속 조사 대상:

1. **메인 도구 호출 수:** Sol 단독은 셸 명령 4회, Astra 단독은 6회, 하네스 메인은 22회였다. 이는 셸 명령 수이며 전체 모델 요청 횟수와 같지 않다.
2. **큰 상태 응답:** 하네스의 성공한 `status` 응답이 3,500 → 9,690 → 28,012 → 37,759자로 커졌다. 마지막 상태의 관측 기록 13개에는 요약 문자열만 합계 26,981자가 있었다. 다음 단계 판단에 필요한 요약과 상세 이력을 분리할 여지가 있다.
3. **추가 상태 조회:** 초기 `NO_ACTIVE_RUN`과 이후 `STALE_REVISION` 응답이 각각 한 번 있었다. 상태를 다시 조회한 작업도 사용량에 포함됐다. 관측 기록 저장과 작업 상태 갱신이 같은 revision을 사용하는 동작을 검토할 필요가 있다.
4. **검토 품질:** 메인은 명세 검토를 통과 근거로 기록했지만 추가 경계값은 놓쳤다. 관리 절차가 많아졌다는 사실만으로 더 나은 검증이 이루어졌다고 판단할 수 없다.

이 항목들은 다음 개선의 후보이며, 각각을 바꿨을 때의 절감 효과를 측정한 결과는 아니다. 우선순위는 작은 작업의 직접 실행 경로 검증, 기본 상태 응답 축약, 반복되는 계획·배정 준비의 도구 호출 감소다.

## 주간 사용량과 본 검증 규모

준비 시작부터 예비 실행 종료까지 계정의 주간 사용률 표시는 **1%p 증가**했다. 이 차이에는 측정 도구를 만든 메인 대화의 작업과 다른 계정 활동이 섞일 수 있다. 개별 Astra·Orchestrail 실행에서는 표시가 변하지 않았지만 사용량이 0이라는 뜻은 아니다. 시작점에서 5%p 증가를 중단 기준으로 잡았고, 이번에는 그 기준에 도달하지 않았다.

세 실행의 합계는 **1,399,459토큰**이다. 똑같은 세 실행을 9번 반복한다는 단순 산술로는 27회에 **12,595,131토큰**이 된다. 이것은 난이도가 다른 세 작업으로 구성된 본 검증의 예측치가 아니다. 주간 한도의 환산 기준도 이번 표시값만으로 추정할 수 없다. 따라서 27회 검증은 자동으로 시작하지 않았다.

## 측정 범위와 재현

메인의 공식 CLI JSON 사용량을 각 대화의 누적 기록과 대조했다. 하위 에이전트는 이 실행의 훅이 제공한 경로만 읽어 ID를 확인하고 마지막 누적 사용량을 한 번만 합산했다. 하네스의 실제 배정 1개와 측정한 하위 대화 1개가 일치했다.

하위 대화 계측은 **CLI 0.154.0에 고정한 실험용 기록 분석**이다. 공식 훅 문서는 기록 파일 형식을 안정적인 인터페이스로 보장하지 않는다. 설치된 플러그인의 일반 `status`에 자동 토큰 계측이 추가된 것은 아니다.

한 번씩 실행했으므로 편차·신뢰구간을 계산할 수 없다. 실행 순서를 무작위로 바꾸거나 서버 캐시를 통제하지도 않았다. 이번 결과로 특정 모델이나 설정의 일반적인 효율을 단정하지 않는다.

재현 방법과 중단 기준: [벤치마크 안내](benchmarking.md). 공개된 자료에는 집계 수치와 도구만 포함하며, 원본 대화·로컬 경로·계정 식별자가 들어 있는 로그는 포함하지 않는다.
